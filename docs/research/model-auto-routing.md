# Route on verifier outcomes, not on prompts

Research cut-off 2026-10-30. Builds on `/home/claude/reports/Factory command center landscape.md` (§5.4 harness table, §7 weak points) and `/home/claude/reports/Amp and Warp philosophy for Vigil.md` (V5 SPRT, V8 scorers). Every number carries the URL the notes recorded; items the notes could not source are omitted; anything that is my reading rather than a source's claim is marked **[inferred]**. Vigil specifics come from the checkout at `/home/claude/vigil` (`vigild/router/rules.py`, `vigild/decider/policy.py`, `configs/routing.yaml`, `configs/backends.yaml`).

**Bottom line.** Every vendor "Auto" mode is a per-prompt classifier whose algorithm, candidate pool and accuracy are unpublished, validated only on the vendor's own single-baseline benchmark, and in three of the four cases (Cursor, Warp, Factory) unusable behind a self-hosted gateway at all. The measured literature says the thing these products do, predict the right model from the prompt, is the weak end for coding agents: prompt-only routing on SWE-bench Verified reaches Route-AUC 0.627 versus 0.780 after reading two turns of the cheap model's trajectory ([alphaXiv](https://www.alphaxiv.org/overview/2607.00053)); lightweight classifiers fall below random on out-of-distribution agentic tasks (RouteLLM-MF 8.93, random 31.25) ([arXiv 2606.22902](https://arxiv.org/pdf/2606.22902)); the strongest chat model is the worst LLM-as-router ([arXiv 2606.22902](https://arxiv.org/pdf/2606.22902)); and on the largest independent benchmark the best learned router buys at most 31.7% cost at parity with the best single model while most routers lose to it ([arXiv 2601.07206](https://arxiv.org/pdf/2601.07206)). What works for code is execution-informed decisions with a verifier the model cannot touch, which Vigil already has. So Vigil should keep its nine deterministic rules as the only thing that *permits* a backend, let Jev *propose* only inside the permitted set on slices that have earned it, derive every threshold from verifier outcomes and replay runs rather than from a classifier, and treat OpenRouter as a pinned-model transport with provider constraints, never as `openrouter/auto`. The minimum evidence before a learned proposer may decide a slice is three full replay repeats of a frozen per-slice set plus a cheap-arm pass rate whose lower confidence bound clears the break-even cost ratio, which on today's noise figures means on the order of fifty verified outcomes per arm per slice **[inferred, derived below]**.

## Vendors route per prompt, disclose nothing, and three of four cannot run behind Vigil's gateway

The thirteen products split cleanly. Four route on prompt content with an unpublished classifier: Cursor Router ("A classifier runs on each agent request and routes by task type and complexity", [Cursor](https://cursor.com/docs/cursor-router.md)), Copilot Auto (a complexity evaluator over "reasoning, code generation complexity, bug diagnosis difficulty, and tool orchestration needs" plus a health system, [GitHub](https://docs.github.com/en/copilot/concepts/auto-model-selection)), OpenRouter Auto Router ("A lightweight classifier assigns each prompt one of about 30 task types", [OpenRouter](https://www.openrouter.ai/docs/model-routing)) and Bedrock Intelligent Prompt Routing (a prompt encoder with per-model quality heads, [arXiv 2509.06274](https://arxiv.org/html/2509.06274v4)). Warp adds an LLM-classified easy/medium/hard bucket under user-written routers ([Warp docs](https://docs.warp.dev/agents/inference/custom-routers.md)); Factory Router escalates mid-session when the model "struggles" by an undisclosed detector ([Factory](https://factory.com/news/factory-router)); LiteLLM ships an inspectable seven-dimension heuristic ([LiteLLM](https://docs.litellm.ai/docs/proxy/auto_routing)). The rest route on rules, state or health: Claude Code (`opusplan`, `fallbackModel`, `availableModels`, [Claude Code docs](https://code.claude.com/docs/en/model-config)), Codex (static `model` and effort, [Codex docs](https://learn.chatgpt.com/docs/config-file/config-sample)), Vercel (uptime and latency, rewrite rules, [Vercel](https://vercel.com/docs/ai-gateway/models-and-providers/provider-options)), Cloudflare (conditional, percentage and budget nodes, [Cloudflare](https://developers.cloudflare.com/ai-gateway/features/dynamic-routing/)) and Portkey (metadata conditions, [Portkey](https://portkey.ai/docs/product/ai-gateway/conditional-routing)). Grok Build has no routing at all; it is the model other routers route *to* as the cheap floor ([x.ai](https://x.ai/news/grok-build-0-1); [Cursor](https://cursor.com/help/models-and-usage/available-models)).

The **published numbers are all vendor single-baseline runs.** Factory reports Router at 99% of Opus 4.7's Terminal-Bench 2 pass rate for 20% lower cost per session and 96% on its own Legacy-Bench for 25% lower, with an unshipped "aggressive" setting at 56% of cost for 81% pass rate; the methodology is Factory's own runs over 89 TB2 tasks ([Factory](https://factory.com/news/factory-router)), and its production claim of 63% aggregate savings compares to "published frontier rates", i.e. to running Opus for everything ([Factory](https://factory.com/news/factory-router-inference-savings)). Warp's WarpBench case cut cost per PR from ~$80 to ~$30 with "no measured quality drop" by moving implementation off Opus 5 to Grok 4.6 then GPT-5.6 Sol, in a post whose task count, run time and run cost are literal "XX" placeholders ([Warp](https://www.warp.dev/blog/warpbench-case-study-reduce-cost-per-pr)). Cursor's 30–50% saving versus Opus 4.8-for-everything and its $6.76 / $4.63 per-commit figures reach us only through a third-party blog because the launch post was unfetchable ([StartDebugging](https://startdebugging.net/2026/07/cursor-router-makes-auto-a-per-request-model-decision/)); the Router docs and changelog contain no figure at all ([Cursor](https://cursor.com/docs/cursor-router.md)). Copilot publishes "better token efficiency with no quality regression" and nothing else ([GitHub](https://github.blog/changelog/2026-05-28-auto-model-selection-now-routes-based-on-your-task-in-vs-code)). Bedrock markets "up to 30%" cost reduction "without compromising accuracy" ([AWS](https://aws.amazon.com/bedrock/intelligent-prompt-routing)); its paper's 43.9% is an offline result on the Claude family with top-1 quality-prediction accuracy above 73% and 36–65 ms routing latency on an A100 ([arXiv 2509.06274](https://arxiv.org/html/2509.06274v4)). OpenRouter publishes no accuracy or cost figure for Auto Router ([OpenRouter blog](https://openrouter.ai/blog/insights/model-routing/)). No vendor publishes routing accuracy against a per-task oracle, a confusion matrix, or the fraction of requests sent to each pool member.

Three design facts matter more to Vigil than the numbers. First, **vendor routers are not available behind a custom endpoint.** Warp's "Auto models always use Warp-provided inference, even with BYOK" and custom routers "can target only concrete models the user can access; not Auto models, other routers, or custom inference endpoints" ([Warp docs](https://docs.warp.dev/agents/inference/custom-routers.md)); Factory Router is an org-gated private research preview that routes among Factory-managed inference, with a BYOK-only mode reserved for enterprise "Require BYOK" and "Factory Private" ([Factory](https://factory.com/news/factory-router-inference-savings)), and Droid itself demands a Factory login outside enterprise even with BYOK ([Factory-AI/factory #451](https://github.com/Factory-AI/factory/issues/451)); Cursor's `agent` needs a vendor key (prior report §5.4). Second, **candidate sets carry hidden mandatory members.** Cursor's router requires Grok 4.6: "Blocking it disables the router" ([Cursor](https://cursor.com/help/models-and-usage/available-models)), which locks out an enterprise whose policy excludes xAI, as a forum user found ([Cursor forum](https://forum.cursor.com/t/which-models-are-behind-cursor-auto-mode/167010)); Copilot Auto may serve "evaluation models" to individual-plan users ([GitHub](https://docs.github.com/en/copilot/concepts/auto-model-selection)); OpenRouter's pool "follows live market spend, not a fixed list" ([OpenRouter blog](https://openrouter.ai/blog/insights/model-routing/)). Third, **the routed model is hidden by default** on Cursor ("Hidden by default and recommended", [Cursor](https://cursor.com/docs/cursor-router.md)) and staff advise pinning a model when predictability matters ([Cursor forum](https://forum.cursor.com/t/which-models-are-behind-cursor-auto-mode/167010)), which is the opposite of a provenance-tagged system.

The useful shapes, as distinct from the routers, are the policy surfaces. Claude Code's `availableModels` + `enforceAvailableModels` + `deniedModels` and the three-deep `fallbackModel` chain are "the full policy surface Claude Code exposes" for a gateway deployment ([Claude Code docs](https://code.claude.com/docs/en/settings-reference)); Bedrock's `responseQualityDifference` is a per-request tolerance τ, "cheapest model within X% of the best predicted" ([AWS docs](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.md)); Copilot routes "along natural cache boundaries" so the unit is a conversation segment, not a request ([GitHub](https://github.blog/changelog/2026-05-28-auto-model-selection-now-routes-based-on-your-task-in-vs-code)); OpenRouter's `provider` object (`order`, `allow_fallbacks`, `zdr`, `data_collection`, `max_price`, `quantizations`, `require_parameters`) is a complete pin ([OpenRouter](https://openrouter.ai/docs/provider-routing)); and Warp's lesson is institutional, not algorithmic: defaults changed only after benchmarking the team's own tasks, with "slice tasks by language, complexity, or client/server" as the next step ([Warp](https://www.warp.dev/blog/warpbench-case-study-reduce-cost-per-pr)), which is Vigil's phase-7 replay by another name.

## The literature: prompt-only routers buy ~30% on QA and collapse on agentic code

The chat-benchmark story that sells routing is real and does not transfer. RouteLLM's matrix-factorization router reached 95% of GPT-4 quality on MT-Bench with 26% GPT-4 calls, cutting cost >85% against GPT-4-only, but on MMLU its routers were "near random" until ~1,500 in-domain golden labels were added, after which the saving was 14% versus random, and on GSM8K it was 35% ([LMSYS](https://lmsys.org/blog/2024-07-01-routellm/)). Hybrid LLM found Llama-2 13b matches or beats GPT-3.5 on ~20% of queries, enough for 22% of calls to go small with <1% BART-score drop, and that single-sample labels are high-variance with ~90% zeros when the large model is much stronger ([arXiv 2404.14618](https://arxiv.org/html/2404.14618v1)). The independent check is LLMRouterBench: 391,645 instances, 21 datasets, 33 models, $2,771.84 of API cost. In the performance-cost setting, OpenRouter's router scored −24.7% versus the best single model (GPT-5), HybridLLM and FrugalGPT also failed to beat it, RouteLLM gained +2.6% accuracy at 11.4% saving, and the best method, Avengers-Pro, gained +4.0% at up to 31.7% saving; top routers sat at 70–72% against a per-query oracle of 91.64%, and on the 11.9% of queries where three or fewer models are correct the best routers scored 23–25% ([arXiv 2601.07206](https://arxiv.org/pdf/2601.07206)). The coding slices are the weak end: HumanEval routers 69.6–76.4 against a 96.8 oracle, LiveCodeBench 49.7–67.3 against 79.7 ([arXiv 2601.07206](https://arxiv.org/pdf/2601.07206)). Even that oracle overstates headroom: a hindsight "any model correct" oracle is a different decision class from a committed router, and on MATH-500 the real premium over the best single model is 3.5 points ([arXiv 2607.03436](https://www.alphaxiv.org/abs/2607.03436)). TrueFoundry's vendor benchmark shows the same shape at the cheap end: a heuristic three-tier classifier retained 98% of all-Opus-5 quality on 550 academic prompts at −69% cost, but only 44% saving on HumanEval, and on a difficulty-labelled set it retained 99% on easy, 79% on medium and 35% on hard items ([TrueFoundry](https://www.truefoundry.com/blog/engineering/llm-cost-routing-benchmark/)).

Three 2026 papers address agentic coding directly, and they agree that the prompt is not enough. **SWE-Router** (ICML 2026) argues an "information-theoretic floor" for prompt-only routing because a similar issue text can hide a typo fix or a multi-module refactor; its router reads K exploratory turns of the weak model's trajectory through a value head trained on the binary unit-test outcome over 400 SWE-bench Verified issues, evaluated on 100. For deepseek-v3.2 → gemini-3-pro the Route-AUC rose from 0.627 at K=0 (prompt only) to 0.780 at K=2, a 15.3-point gain, and K=3 curves sit above the random-assignment ±1σ band; but on SWE-Smith the gpt-5-mini router did not beat baselines, attributed to repository-based distribution shift, and the strong model restarts from the original prompt, so exploration cost is sunk ([arXiv 2607.00053](https://arxiv.org/abs/2607.00053); [alphaXiv](https://www.alphaxiv.org/overview/2607.00053)). **Agent-as-a-Router / ACRouter** routes among eight models with a fine-tuned Qwen3.5-0.8B plus heuristics, a sandbox verifier and a kNN memory over verified outcomes; in distribution it scores 49.98 versus 43.83 for always-Opus-4.6 at $13.21 versus $34.02, and on 176 OOD agentic tasks 62.50 versus 57.14 at $52.97 versus $89.28, while RouteLLM-BERT and RouteLLM-MF fall to 21.43 and 8.93 against random 31.25, "dimension identity explains roughly 27% of the entropy of the oracle's choice", zero/few-shot LLM routers choose nearly uniformly, and Claude Opus 4.6 ranks last as a router (39.27 / 41.17); a standalone GPT-5.4 run resolved 75.00% of the OOD tasks, above the router ([arXiv 2606.22902](https://arxiv.org/pdf/2606.22902)). **Triage** proposes exactly Vigil's intake features (code health, test coverage of changed code, files the issue names) over SWE-bench Lite with a 50-task pilot and 300 × 3 tiers × 3 runs, and states the go/no-go arithmetic: the light tier's pass rate must exceed the cost ratio c_L/c_H, ~20% for Haiku→Opus; it has no results yet ([arXiv 2604.07494](https://arxiv.org/pdf/2604.07494)). Vendor field data point the same way: Faros found the aggregate-best (model, harness) route was best on only 84 of 211 real tasks (40%), with a 43-point mean best-versus-worst gap, and rankings shifted between two releases two weeks apart after a provider-side caching fix ([Faros](https://www.faros.ai/blog/is-intelligent-model-routing-enough)); Databricks reports Sonnet 5 at 1.7× cheaper per token costing $2.09 per task against Opus's $1.94 because it uses ~1.9× the tokens, with 81% versus 87% completion, and fixes the model per task to preserve prompt-cache hits ([BestHub](https://www.besthub.dev/articles/why-giving-agents-the-strongest-model-by-default-is-wasteful-databricks-introduces-joint-model-and-harness-selection-4885c6c7381f)).

Cascades with execution feedback have the only clean positive results on code. The self-testing code cascade (small model generates k solutions and k test suites, escalates when agreement falls below θ) cut cost 26% on average and up to 70% while a 76.7% cascade beat the 34B model alone at 72.6%; models under ~10% accuracy produced false-positive tests and should be excluded, and "question difficulty shows no clear link to average savings" ([arXiv 2405.15842](https://arxiv.org/html/2405.15842v2)). The caveat is who grades the cheap attempt. Silent semantic failure accounts for 80% of Llama 4's and 68% of GPT-5's failing agent runs, and completion- or consistency-based monitors "look healthy when the agent should not be trusted" ([agentpatterns citing arXiv 2603.25764](https://agentpatterns.ai/patterns/agent-design/per-task-agent-routing/)); 22 of 81 runs cut off at a 1,200 s ceiling still produced passing patches, so completion and correctness are separate endpoints ([arXiv 2609.11987](https://arxiv.org/pdf/2609.11987)); and GPT-4-class judges rate their own outputs with recall 0.945 on human-preferred versus 0.425 on human-dispreferred ones, a self-preference gap of 0.52 ([arXiv 2410.21819](https://arxiv.org/pdf/2410.21819)), with capability uncorrelated or negatively correlated with low self-preference across 20 LLMs ([arXiv 2604.22891](https://arxiv.org/abs/2604.22891)).

Harness choice is the larger cost lever and the smaller quality lever. On 50 Terminal-Bench Pro tasks, OpenCode used ~40× the tokens per solved task of Goose (40.8× on Qwen 3.6 Plus, 41.9× on MiniMax M2.5) while pass-rate spread across harnesses was 2–8 pp and every pairwise CI but one included zero ([arXiv 2607.22585](https://arxiv.org/pdf/2607.22585)); a neutral LangGraph harness cost 1.3–1.6× per solve versus claude-agent-sdk on Opus 4.8 and ~1.2× versus the Codex SDK on GPT-5.5, with cost per solve from $2.88 to $5.07, and same-model harness contrasts of ±1.25 pp inside CIs of [−10.0, +7.5] ([arXiv 2609.11987](https://arxiv.org/pdf/2609.11987)). The practitioner synthesis is to route harnesses "on token budget, latency and known failure mode, not capability" ([agentpatterns](https://agentpatterns.ai/patterns/agent-design/per-task-agent-routing/)).

Finally the noise floor, which bounds every threshold below. On SWE-bench Verified (N=500), 60,000 trajectories across 6 configurations × 10 runs showed single-run pass@1 ranges of 2.2–6.0 points and SDs of 0.7–1.8 points, unchanged at temperature 0; at σ=1.5 and 80% power, a 2-point difference needs 9 runs per arm (p<.05) and a 1-point difference 36 ([arXiv 2602.07150](https://arxiv.org/html/2602.07150v2)). On a single task, 584 runs gave a sizing rule of 16·sd²/gap², three-run averages mis-ranked same-model pairings 28–44% of the time, and one-run-each favoured the smaller model 28% of the time ([agentpatterns summarising arXiv 2609.33812](https://agentpatterns.ai/verification/size-agent-comparisons-by-run-variance/)). Prompt rewording moves results 11–58× more than reruns ([agentpatterns summarising arXiv 2608.22331](https://agentpatterns.ai/verification/size-agent-comparisons-by-run-variance/)). Practitioner guidance: three independent repeats as the minimum, paired items, McNemar for pass/fail, never credit a difference smaller than the measured run-to-run spread, pin model versions ([arXiv 2608.13867](https://arxiv.org/pdf/2608.13867)). And the price of a fixed capability falls ~47% per quarter, ~13× a year ([Epoch AI](https://epoch.ai/publications/the-plunging-price-of-thought)), so any calibrated threshold is stale within a quarter.

## Verdict: for coding agents, execution-informed cascades beat prediction, and Vigil already owns the piece that makes cascades safe

The evidence supports a hybrid in which prediction gates only the obvious cases and execution decides the rest. **Predictive routing from the prompt has a floor** that the best paper on the subject names and measures: 0.627 Route-AUC at K=0 against 0.780 after two cheap turns ([alphaXiv](https://www.alphaxiv.org/overview/2607.00053)); the only task-feature evidence is 27% of oracle entropy from task dimension ([arXiv 2606.22902](https://arxiv.org/pdf/2606.22902)), and nothing has been published on Terminal-Bench or Aider routing by feature at all. **Prediction still earns its place at the extremes.** Vigil's rules 2 and 3 (money and architecture → Opus) are the "skip the cheap attempt" branch, and a deterministic hard rule is both cheaper and more auditable than Bedrock's encoder for that purpose; the question is only what to do with the undecided middle, rules 6–9, where the router today sends labelled S/M work to the tower and everything else to Sonnet ([`rules.py`](/home/claude/vigil/vigild/router/rules.py)).

**Cascades fail in the literature for one reason Vigil has removed.** FrugalGPT-style cascades lost to the best single model on LLMRouterBench ([arXiv 2601.07206](https://arxiv.org/pdf/2601.07206)) and the code cascade's escalation signal is the small model's own generated tests ([arXiv 2405.15842](https://arxiv.org/html/2405.15842v2)), which is exactly the gate that silent semantic failure (68–80% of failing runs, [agentpatterns](https://agentpatterns.ai/patterns/agent-design/per-task-agent-routing/)) and judge self-preference (0.52 recall gap, [arXiv 2410.21819](https://arxiv.org/pdf/2410.21819)) corrupt. Vigil's verifier runs base, before and after in a fresh vault checkout with the repo's dev image and hidden tests the worker never saw (`CLAUDE.md` gotchas; prior report V8), so a cheap attempt's pass or fail is a label no model produced. **[inferred]** That turns the cascade's open problem into arithmetic: route cheap-first on a slice when P(cheap passes the verifier) exceeds cost_cheap_attempt / cost_strong_attempt, with cost_cheap_attempt measured from the gateway rather than from list price, because a cheaper model can cost more per task through longer runs (Databricks's 1.9× tokens, [BestHub](https://www.besthub.dev/articles/why-giving-agents-the-strongest-model-by-default-is-wasteful-databricks-introduces-joint-model-and-harness-selection-4885c6c7381f)). Triage states the same gate as ~20% for Haiku→Opus ([arXiv 2604.07494](https://arxiv.org/pdf/2604.07494)); for a tower-local arm whose marginal cost is electricity the ratio approaches zero and the gate becomes "does it pass often enough to be worth the wall time and the verifier run" **[inferred]**.

The remaining cost of a cascade is the sunk cheap attempt, and here Vigil's own budget rules shape the design. The per-task cap is $2 ([`CLAUDE.md`](/home/claude/vigil/CLAUDE.md)), so a cheap attempt plus a strong restart must fit under it or the escalation becomes a new attempt. Rule 5 already escalates at `attempt >= 3` or `review_rounds >= 2` ([`rules.py`](/home/claude/vigil/vigild/router/rules.py)); **[inferred]** a verifier-gated cascade is rule 5 with the attempt threshold lowered to 2 on graduated slices, nothing structurally new. SWE-Router's early-trajectory abort, a value head reading two turns and predicting P(resolve) ([alphaXiv](https://www.alphaxiv.org/overview/2607.00053)), is the later refinement that caps sunk cost, and it is a typed question Jev could answer, but it would send trajectory text to a hosted decider, which on a private repo is only permitted through `jev-cloudflare` ([`repos.py`](/home/claude/vigil/vigild/repos.py)); it belongs after the simpler cascade has data, not before.

One more piece of the verdict concerns the proposer itself. The reason to use Jev rather than a chat model is measured: zero- and few-shot LLM routers choose nearly uniformly and the strongest model is the worst router ([arXiv 2606.22902](https://arxiv.org/pdf/2606.22902)), whereas a decision model returns a calibrated probability over a typed choice, which the decider policy already thresholds at 0.85 to act and 0.6 to escalate to Haiku ([`policy.py`](/home/claude/vigil/vigild/decider/policy.py)). But calibration is a claim to be tested, not assumed: the design's decider eval already plans to score "calibration (does 0.85 confidence mean 85% right)" against the owner's labels ([`design.md`](/home/claude/vigil/docs/design.md)), and the routing `tier` question must pass that same test before any of its answers are acted on.

## Minimum evidence before a learned proposer may decide a slice

No paper reports a learning curve of outcomes-needed-to-beat-a-rule for coding agents; the bounds have to be assembled from the noise studies and the sample sizes the routing papers used. The direct data points: ~1,500 in-domain labels moved RouteLLM from chance to useful on MMLU ([LMSYS](https://lmsys.org/blog/2024-07-01-routellm/)); SWE-Router trained on 400 issues and still failed across repositories ([alphaXiv](https://www.alphaxiv.org/overview/2607.00053)); ACRouter warmed a kNN memory on 200 verified tasks after a 7,080-task probing set, and its online bandits held 46–50% OOD where static classifiers collapsed ([arXiv 2606.22902](https://arxiv.org/pdf/2606.22902)); Triage sets a 50-task pilot as its go/no-go ([arXiv 2604.07494](https://arxiv.org/pdf/2604.07494)); and at the benchmark level 9 runs of 500 tasks detect a 2-point gap ([arXiv 2602.07150](https://arxiv.org/html/2602.07150v2)). **[inferred]** In Vigil's regime (two repos, tens of tasks a week, a binary verifier label per attempt) a trained router of any kind is data-starved for months, so the question is not "when can a model be trained" but "when is a per-slice pass-rate estimate tight enough that choosing by it beats the hand rule", which is what the bandit literature reduces to at low N and what ACRouter's memory is: an average over verified neighbours.

**Define the slice first.** The unit of evidence must be the thing the rules already name: (repo, shape label, size), e.g. `(parkagent, tests, S)`, because the OOD failures are per repository ([alphaXiv](https://www.alphaxiv.org/overview/2607.00053)) and Faros found the best route varies by repository domain, work type and complexity ([Faros](https://www.faros.ai/blog/is-intelligent-model-routing-enough)). A slice that pools repos pools their shift **[inferred]**.

**The gates, with the arithmetic that sets them [inferred, derived from the sources above].** A slice may graduate from "rules only" to "proposer may choose inside the permitted set" when all of the following hold, and it demotes the moment any fails.

1. *Replay repeats.* The slice has a frozen replay set of at least 20 tasks (the design's "20-task replay" and "ten replayed issues per quarter", [`design.md`](/home/claude/vigil/docs/design.md)), and every candidate arm has run it at least 3 times, the practitioner minimum ([arXiv 2608.13867](https://arxiv.org/pdf/2608.13867)); differences are judged by McNemar on paired tasks and never credited below the measured run-to-run spread. Three repeats of 20 tasks is 60 outcomes per arm; three-run averages still mis-rank 28–44% of the time on single tasks ([agentpatterns](https://agentpatterns.ai/verification/size-agent-comparisons-by-run-variance/)), so repeats establish the spread, not the winner.
2. *Outcome count.* At least 50 verifier outcomes per candidate arm in the slice, counting production attempts and replay runs, with no single task contributing more than 3. With 50 Bernoulli outcomes at a pass rate near 0.8 the 95% interval is roughly ±11 points; at 30 it is ±14; at 100 it is ±8. Fifty is where a cheap arm at a true 0.6 can be told from a break-even of 0.3 (the Haiku→Opus ratio of ~20% plus the 1.9× token inflation) with the lower bound clear, and it matches Triage's pilot and ACRouter's warm-up order of magnitude.
3. *Break-even with margin.* The cheap arm's lower 95% Wilson bound on verifier pass rate exceeds cost_cheap/cost_strong, both measured from gateway metering over the same slice, by at least 10 points. For the tower arm the ratio is near zero, so the test becomes a floor: the lower bound must exceed 0.5, below which the sunk wall time and verifier runs exceed what the slice saves **[inferred]**.
4. *No quality regression beyond noise.* Across the three repeats, the cheap arm's pass rate on the frozen set is within the measured spread of the strong arm's, or the cascade (cheap then strong on failure) matches the strong arm's pass rate, which is the comparison that matters once escalation exists. Bedrock's τ is the same shape: cheapest within a tolerance of the best ([AWS docs](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.md)).
5. *Proposer calibration on the slice.* Jev's `tier` answers in shadow on this slice number at least 50, and among answers with probability ≥ 0.85 the fraction whose proposed arm went on to pass the verifier is at least 0.80. This is the design's planned calibration check applied per slice ([`design.md`](/home/claude/vigil/docs/design.md)). An uncalibrated proposer stays in shadow regardless of how good the arms look.
6. *Freshness.* No change to the arm's model string in `backends.yaml`, its price in `prices.yaml`, the harness pin, or the repo's dev image since the last replay. Rankings moved within two weeks on a provider-side change ([Faros](https://www.faros.ai/blog/is-intelligent-model-routing-enough)) and price falls 47% a quarter ([Epoch AI](https://epoch.ai/publications/the-plunging-price-of-thought)); any such change demotes the slice to shadow until gate 1 is rerun.

**Demotion** uses a rolling window, not a one-off: the last 20 production outcomes on the slice. If the chosen cheap arm's pass rate in that window drops below the break-even by the same 10-point margin, or two consecutive escalations occur on a slice graded "cheap", the slice returns to rules-only and the event opens an inbox item. **[inferred]** The sequential alternative is the SPRT the earlier report defined for the review ladder (p0 = 0.80, p1 = 0.95, α = 0.05, β = 0.10; 17 consecutive catches promote) ([Amp and Warp report, V5](/home/claude/reports/Amp%20and%20Warp%20philosophy%20for%20Vigil.md)); routing can reuse that machinery with p0 and p1 set to the break-even and the strong arm's observed rate, which gives the owner one statistical test to read instead of two.

## Failure modes Vigil must design around

**Per-repo distribution shift is the dominant risk.** SWE-Router's router passed validation and failed its test set across repositories ([alphaXiv](https://www.alphaxiv.org/overview/2607.00053)); static classifiers trained on a probing set fell below random on agentic OOD tasks ([arXiv 2606.22902](https://arxiv.org/pdf/2606.22902)). Vigil has two repos today and a private one whose text may not leave the host except to `jev-cloudflare` ([`repos.py`](/home/claude/vigil/vigild/repos.py)). The defence is to key every routing statistic per (repo, shape, size) and never let a slice graduate on another repo's evidence; a new repo starts at rules-only with zero history.

**Provider drift and silent model updates.** Faros's rankings changed in two weeks after a provider-side caching fix with no change to tasks or model names ([Faros](https://www.faros.ai/blog/is-intelligent-model-routing-enough)); offline routers "need re-labeling and re-training when the query distribution or model pool changes" ([arXiv 2603.30035](https://arxiv.org/html/2603.30035v1)). Vigil's pins by exact model string are necessary but not sufficient because providers update behind a string; the gateway should record the provider's returned model/version field on every call and treat a change as a freshness break (gate 6). OpenRouter's response carries the `model` actually used ([OpenRouter blog](https://openrouter.ai/blog/insights/model-routing/)); Bedrock's response includes the model used ([AWS docs](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.md)).

**LLM-as-router self-preference and judge leniency.** The strongest chat model is the worst router ([arXiv 2606.22902](https://arxiv.org/pdf/2606.22902)); judges prefer their own output by a 0.52 recall gap ([arXiv 2410.21819](https://arxiv.org/pdf/2410.21819)); structured protocols cut the bias only 31.5% ([arXiv 2604.22891](https://arxiv.org/abs/2604.22891)). Vigil's `needs_escalation` question ("Do these review findings need escalation to a stronger model?", [`questions.py`](/home/claude/vigil/vigild/decider/questions.py)) is the one place a model opinion touches routing; it must never be answered by the model whose work is under review, and its answer should remain a proposal that the verifier result can overrule.

**Price changes invert the cheap arm.** A per-token price is not a per-task price: Sonnet 5 at 1.7× cheaper per token cost more per task than Opus ([BestHub](https://www.besthub.dev/articles/why-giving-agents-the-strongest-model-by-default-is-wasteful-databricks-introduces-joint-model-and-harness-selection-4885c6c7381f)); a cheap harness can use 40× the tokens ([arXiv 2607.22585](https://arxiv.org/pdf/2607.22585)). Every break-even must use gateway-metered dollars per attempt, with cache reads and writes counted the way the provider bills them ([arXiv 2609.11987](https://arxiv.org/pdf/2609.11987) warns about cache-inclusive versus exclusive token semantics), and a `prices.yaml` edit must invalidate the slice.

**Label noise.** One verifier run is one Bernoulli draw with SD 0.7–1.8 points at the benchmark level ([arXiv 2602.07150](https://arxiv.org/html/2602.07150v2)); Hybrid LLM needed 10 samples per query for usable labels ([arXiv 2404.14618](https://arxiv.org/html/2404.14618v1)). Vigil must accumulate per slice, never decide per task, and the replay must cap any single task's contribution.

**Mid-task model switching.** Factory escalates mid-session ([Factory](https://factory.com/news/factory-router)); Copilot re-routes at cache boundaries ([GitHub](https://github.blog/changelog/2026-05-28-auto-model-selection-now-routes-based-on-your-task-in-vs-code)); Warp's own guide says switching mid-conversation resets prompt caching ([Warp docs](https://docs.warp.dev/guides/configuration/how-to-use-tokens-efficiently-with-ai-coding-agents.md)) and Databricks fixes the model per task for that reason ([BestHub](https://www.besthub.dev/articles/why-giving-agents-the-strongest-model-by-default-is-wasteful-databricks-introduces-joint-model-and-harness-selection-4885c6c7381f)). SWE-Router's escalation restarts from the original prompt and treats the cheap turns as sunk ([alphaXiv](https://www.alphaxiv.org/overview/2607.00053)). Vigil's unit should stay the attempt: one model per attempt, escalation as a new attempt in a fresh container, which is also what makes the evidence row clean.

**Harness-side fallbacks that bypass the router.** Claude Code's `fallbackModel` chain and the Max usage-threshold Opus→Sonnet switch ([Claude Code docs](https://code.claude.com/docs/en/model-config); [#19371](https://github.com/anthropics/claude-code/issues/19371)), Warp's BYOK "credit fallback" to vendor inference ([Warp docs](https://docs.warp.dev/agents/cli/models-and-usage/)) and OpenRouter's default provider routing (weighted random across providers, [OpenRouter](https://openrouter.ai/docs/provider-routing)) each let the model change without the router knowing. **[inferred]** In the executor image, `availableModels` should list exactly the session's assigned preset alias with `enforceAvailableModels: true` and no `fallbackModel`, and the gateway should refuse any model id other than the one on the session token.

**Oracle inflation and model-recall failure.** Headroom estimated from a hindsight oracle overstates what a committed router can get (3.5 points on MATH-500, [arXiv 2607.03436](https://www.alphaxiv.org/abs/2607.03436)), and on the hardest slice routers are wrong three times in four ([arXiv 2601.07206](https://arxiv.org/pdf/2601.07206)). Vigil's scoreboard should report the gap between the chosen arm and the best *committed* arm on the same frozen set, never against "any arm passed".

**Mandatory and hidden pool members.** Cursor's mandatory Grok and hidden routed model ([Cursor](https://cursor.com/help/models-and-usage/available-models)), Copilot's evaluation models ([GitHub](https://docs.github.com/en/copilot/concepts/auto-model-selection)) and OpenRouter's spend-following pool ([OpenRouter blog](https://openrouter.ai/blog/insights/model-routing/)) are each a provenance and private-repo violation in Vigil's terms: `check_backend` cannot vet a backend it does not know in advance ([`rules.py`](/home/claude/vigil/vigild/router/rules.py)).

**Gaming.** No paper studies adversarial prompts that look easy to a router (notes, KQ5 gaps). Vigil's intake is owner-approved specs, and untrusted text enters packets only through `packets.fence()` ([`CLAUDE.md`](/home/claude/vigil/CLAUDE.md)), which bounds the surface; the rules that matter (money, architecture) key on file paths and labels, not prose, so a prompt cannot talk its way to a cheaper tier **[inferred]**.

## Recommendation for Vigil in four stages

The principle, stated once: **rules permit, evidence decides, Jev proposes.** The nine rules stay deterministic and first-match-wins, and they remain the only code that can put a backend on the table. What changes is that rules 6–9 learn to emit a *permitted set* alongside their default, that every attempt writes an evidence row, and that a proposer is allowed to pick inside the permitted set only on slices that have passed the gates above. Rules 1–3 (spec, money, architecture) and rule 5 (escalation) emit a singleton and are never proposable; `LOCAL_OK` on a money path stays a refusal ([`rules.py`](/home/claude/vigil/vigild/router/rules.py)). The private-repo rule applies to the permitted set before any proposer sees it, and a local session never carries a hosted preset in its set.

### Stage 0, now: log everything the later stages need

Nothing routes differently. Every attempt gets an evidence row keyed by slice `(repo, shape, size)` and arm `(preset, model string as returned by the provider, harness pin, prompt revision)`, carrying: the rule name and `tier_reason` already produced; the permitted set; the preset actually used and why (rule, fallback for a non-live preset, or override); gateway-metered input, output, cache-read and cache-write tokens and dollars per attempt; wall time and tool-call count; the verifier verdict as base/before/after JUnit comparison; review rounds and attempt number; the post-merge 48-hour result and the 30-day attribution the design already plans ([`design.md`](/home/claude/vigil/docs/design.md)); and `provenance`. This is what Scaffold Effect asks every eval to report (tokens per solved task, no-action turns, failure categories, [arXiv 2607.22585](https://arxiv.org/pdf/2607.22585)) and what Harness-or-Model says to price from (raw per-turn usage, [arXiv 2609.11987](https://arxiv.org/pdf/2609.11987)). Add two columns the vendors hide: `requested_model` versus `served_model`, and the provider endpoint when a preset is OpenRouter.

### Stage 1, shadow: Jev answers, nobody acts

The decider's existing `tier` question (choice among `claude-opus`, `claude-sonnet`, `local`, `local-fast`, [`questions.py`](/home/claude/vigil/vigild/decider/questions.py)) is asked on every task whose rule is 6–9, with the permitted set as its options, and the answer, probability, backend and `model_version` are written to `decisions` with action `wait` regardless of probability. Shadow also records the counterfactual that matters for a cascade: whether the cheapest permitted arm *would* have been tried first. Private repos ask only `jev-cloudflare`; public repos may use `jev-openrouter` pinned at `typesafe/jev-1.13` through the Decisions API with `provider.zdr` ([`design.md`](/home/claude/vigil/docs/design.md); [`backends.yaml`](/home/claude/vigil/configs/backends.yaml)). Shadow runs until gate 5 (≥ 50 answers per slice, calibration ≥ 0.80 at the 0.85 threshold) can be evaluated; nothing in this stage touches routing. LiteLLM's documented use of Jev as a tier classifier with a circuit breaker on timeout ([LiteLLM](https://docs.litellm.ai/docs/proxy/auto_routing)) is a precedent that it works as a request-path classifier; Vigil's difference is that the answer is scored against a verifier label rather than trusted.

### Stage 2, yardstick: the weekly replay becomes the routing evidence

Phase 7's replay ([`design.md`](/home/claude/vigil/docs/design.md), "Eval protocol") runs each slice's frozen set against every permitted arm, three repeats, inside the replay's own `budgets.yaml` line, with the bench approval label. The scoreboard reports per slice and arm: verifier pass rate with a Wilson interval, dollars per attempt and per solve, tokens per solved task, wall time, and the cascade's pass rate and cost (cheap then strong on failure) computed from the paired runs. The decision rule it prints is Bedrock's shape turned into evidence: the cheapest arm whose lower bound is within the measured spread of the best arm ([AWS docs](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.md)), and Triage's break-even line ([arXiv 2604.07494](https://arxiv.org/pdf/2604.07494)). Output is evidence rows and a proposed `routing.yaml` diff as a draft PR the owner merges, exactly as the design already mandates ("routing.yaml and review.yaml edited from results by PR", [`design.md`](/home/claude/vigil/docs/design.md)). This is WarpBench without the LLM judge: Warp's own case shows defaults should move only after measuring on your own tasks ([Warp](https://www.warp.dev/blog/warpbench-case-study-reduce-cost-per-pr)), and Vigil's scorer is the verifier rather than a transcript reader (prior report V8).

### Stage 3, bounded decide per slice

A slice that passes all six gates gets a line in `routing.yaml` such as `graduated: {parkagent/tests/S: {permitted: [local, claude-sonnet], cheap_first: true}}` **[inferred shape]**. On that slice only, the rule still fires first and emits the permitted set; the proposer's `tier` answer is acted on if its probability clears 0.85 and its choice is in the set, otherwise the rule's default stands; `cheap_first: true` makes the first attempt the cheapest permitted arm and a verifier failure escalates to the next arm as a new attempt (rule 5 with its threshold at 2 for this slice), the whole chain bounded by the $2 task cap and the daily and monthly hard stops ([`CLAUDE.md`](/home/claude/vigil/CLAUDE.md)). The demotion window and the freshness break apply automatically; an owner's `--tier` override is still refused on rule 2 and still logged on anything else. Nothing here is a learned model: the proposer is Jev, the thresholds are from evidence rows, and the owner merged the graduation. SWE-Router's early-trajectory abort can be added later as a second typed question ("will this attempt pass?") asked after two turns on slices where the sunk cost of a full cheap attempt is material, but only on public repos or through `jev-cloudflare`, and only after its own shadow period.

### Stage 4, harness in the choice set

Once OpenCode is a worker (phase 2 in the prior report's §5.4), the arm becomes `(preset, harness)` and the yardstick compares pairs. Route harnesses the way the evidence says: on tokens per solve, wall time and failure fingerprint, not on pass rate, because the measured harness pass-rate spread (0–8 pp) is inside noise while the token spread is 40× ([arXiv 2607.22585](https://arxiv.org/pdf/2607.22585); [agentpatterns](https://agentpatterns.ai/patterns/agent-design/per-task-agent-routing/)). The admission test for any further harness is the prior report's: keyless, pointed at the gateway, inside the egress-locked container. **Droid and Warp CLI do not warrant adapters on current evidence.** Droid's BYOK still requires a Factory browser login and may sync settings to Factory's cloud ([Z.AI docs](https://docs.z.ai/devpack/tool/droid.md); [#451](https://github.com/Factory-AI/factory/issues/451)), its router is org-gated and tied to Factory inference ([Factory](https://factory.com/news/factory-router-inference-savings)), and whether `droid exec` runs with zero Factory token is unverified (notes, KQ3 gaps); Warp's Auto modes always use Warp inference and its routers cannot target custom endpoints ([Warp docs](https://docs.warp.dev/agents/inference/custom-routers.md)). Neither brings a router Vigil can use, so each would be one more harness with its own permission model and failure catalogue, the cost agentpatterns warns about ([agentpatterns](https://agentpatterns.ai/patterns/agent-design/per-task-agent-routing/)). Grok Build's single model is a candidate *preset* behind the gateway (it is already on OpenRouter and Vercel, [x.ai](https://x.ai/news/grok-build-0-1)), and its CLI a candidate harness only if the prior report's Q4 spike passes.

### How OpenRouter should and should not be used

**Never `openrouter/auto` or `auto-beta`.** It ranks by the community's trailing-7-day spend share per task type ([OpenRouter](https://www.openrouter.ai/docs/model-routing)), a popularity signal, not a quality one; it scored −24.7% against the best single model on LLMRouterBench ([arXiv 2601.07206](https://arxiv.org/pdf/2601.07206)); the pool "follows live market spend" ([OpenRouter blog](https://openrouter.ai/blog/insights/model-routing/)), so the model is unknown until the response, which breaks the private-repo check, the exact-version pin, provenance and the evidence row all at once. **Use OpenRouter as a pinned transport.** Each `openrouter` preset in `backends.yaml` names one exact model id (the current entry has `model: null` and `live: false`, [`backends.yaml`](/home/claude/vigil/configs/backends.yaml)), and the gateway sends `provider: {order: [<one or two named providers>], allow_fallbacks: false, zdr: true, data_collection: "deny", require_parameters: true, max_price: {...}, quantizations: [...]}` so that provider selection is not the default weighted-random walk ([OpenRouter](https://openrouter.ai/docs/provider-routing)). A `models` fallback array is acceptable only when every entry is itself an allowlisted preset for the repo, and the served `model` field is recorded as the arm, because "you are billed only for the model that actually runs" means the evidence row must name that model ([OpenRouter blog](https://openrouter.ai/blog/insights/model-routing/)). `allowed_models`/`excluded_models` are a second fence, not the first: `check_backend` runs before the request leaves vigild. The Decisions API with `typesafe/jev-1.13` is the one OpenRouter product that fits the decider, and it is "not a chat model, a coding agent, or a replacement for the LLM that drives one" ([skills.sh](https://www.skills.sh/openrouterteam/skills/openrouter-decisions)), which is exactly the boundary Vigil wants.

### Where Jev fits, precisely

Jev is a proposer in three places and a decider in none of them. It answers `tier` inside the permitted set (stage 1 shadow, stage 3 bounded), `needs_escalation` on review findings as a proposal the verifier can overrule, and later the early-abort question. It never sees a choice the rules did not permit, never answers on a private repo except through `jev-cloudflare`, and its every answer is a `decisions` row with a probability that the scoreboard scores against the verifier. The calibration gate is per slice because the design's planned decider eval is a 10-spec, 20-issue launch set ([`design.md`](/home/claude/vigil/docs/design.md)), which is enough to pick a backend and not enough to trust it on a shape it has not seen.

## Conclusion

The routing question for Vigil turns out not to be a modelling question. Every router that works in print works because it has a trustworthy label, and every router that fails fails because its label is the prompt or the model's opinion of itself. Vigil's verifier is a labelling machine the vendors do not have, which means the cheapest routing policy Vigil can run, cheap arm first on a slice whose pass rate has been measured, is also the one with the best evidence behind it, and the expensive routers the vendors sell are solving a problem Vigil does not have, how to guess without executing.

Two things follow that the plan does not yet say. First, the replay's frozen sets should be built per slice from the start, because the sample-size arithmetic is per slice and a 20-task set that mixes shapes graduates nothing. Second, the first graduation candidates are not the ones that save the most money but the ones where the cheap arm's cost is nearest zero and the label is cleanest: `tests`, `docs` and `lint` on the tower, where the break-even floor is wall time and the verifier runs the suite the task itself touched. If the tower cannot clear a 0.5 lower bound there, no amount of routing cleverness will make it a worker, and the design's own fallback, Sonnet by rule 9, is the right answer at zero engineering cost.
